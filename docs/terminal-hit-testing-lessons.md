# 终端选择功能排查记录：四个缺陷与一次误诊

> 日期：2026-08-26 · 涉及模块：`n3ri-ui/src/apps/terminal.rs` · 提交：`6c20161`, `4f697c1` 及后续修复

## 背景

为终端实现 web 风格的选择复制（逐行渲染重构 + 字形反查命中 + arboard 剪贴板）后，
连续四轮实测反馈暴露了四个互相独立的缺陷。其中一轮包含一次**错误的诊断**，值得完整复盘。

## 症状时间线与根因

| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | 向上滚正常，向下滚完全不动；滚上去后看不到最新输出 | `(负浮点) as usize` 饱和为 0，向下滚动变成 `saturating_sub(0)` 恒零操作 | 经 `isize` 中转正负分流 |
| 2 | 输出过长时最新内容差十几行才进入视野 | 视口行数 = 容器高 ÷ 硬编码 `LINE_HEIGHT(18.0)`，真实行距 ≠ 常量时估算偏多，多出的行被裁切 | 从已布局行实体的 `ComputedNode.size().y` 实测行距，自校准 |
| 3 | 选择高亮相对鼠标向上漂移若干行；**短输出时双击完全无法选中** | 命中检测把**逻辑像素**光标坐标喂给**物理像素**空间的 `ComputedNode` 几何（见下文） | `cursor_position()` → `physical_cursor_position()`，与 bevy_ui 官方契约对齐 |
| 4 | （误诊）曾把 #3 归因于"系统执行顺序竞态" | 见"误诊复盘" | 引入渲染系统独占写入 `TerminalLine.li`——无害的工程改良，保留，但不是病灶 |

## 核心教训 1：坐标空间契约（本次最贵的一课）

Bevy 0.19 中存在两套像素坐标，混用不报错、只在缩放 >100% 的屏幕上出错：

| API | 空间 |
|---|---|
| `Window::cursor_position()` | **逻辑**像素（physical ÷ scale_factor） |
| `Window::physical_cursor_position()` | 物理 |
| `ComputedNode` / `UiGlobalTransform` / `TextLayoutInfo` | **物理** |

权威依据（本地 cargo registry 源码可查）：

- `bevy_ui/src/focus.rs`：官方命中检测链路用 `window.physical_cursor_position()`
- `bevy_ui/src/ui_node.rs`：`ComputedNode::inverse_scale_factor` 文档明示节点几何在物理空间

错配的症状特征：**误差随离窗口左上角的距离线性放大**（乘了 scale_factor 的差）。
靠近原点的元素看似正常，越远偏得越多；缩放 100%（sf=1.0）的开发机上完全无法复现。

推论：本项目其他系统（窗口拖拽、resize、snap）拿 `Node` **样式值**（逻辑）对比
`cursor_position()`（逻辑），恰好自洽所以一直正常。同一工程内两种比较并存，
"别处都对"不能证明坐标系用法正确。

**规则：与 ComputedNode/变换做几何运算，一律用 `physical_cursor_position()`；
与 Node 样式 Val 做运算，用 `cursor_position()`。**

## 核心教训 2：误诊复盘——假设必须解释全部症状

#3 的第一轮诊断是"selection 与 render 系统被 sync_output 交错，各自计算映射产生竞态"。
该理论能解释"长输出时向上漂移"（输出流每帧 +K 行），修复（实体直读 li）也确实更合理，
但**没有治好病**。

真正锁死根因的是用户补充的关键鉴别症状："**平时的短输出根本无法双击出现复制框**"。

- 竞态假设预测：短输出时系统间交错少，应基本正常 —— 与事实矛盾 ✗
- 坐标错配假设预测：短输出集中在容器顶部，点击换算后落到容器外 → 全部无命中 ✓
- 且坐标假设同时解释"偏移量随点击位置变化"（线性增长）而竞态假设解释不了这一点

**规则：提出假设后，用它推演每一个已知症状，尤其是"最极端/最反直觉"的那个。
只能覆盖部分症状的假设，无论多么自洽，都是错的或次要的。**
另外：验证 Bevy 行为不要凭记忆猜——直接读 `~/.cargo/registry` 里对应版本的源码
（focus.rs / ui_node.rs 各花两分钟），是本次从"循环猜测"跳到"锤实结论"的分水岭。

## 核心教训 3：浮点转无符号整数的饱和陷阱

```rust
let lines_to_scroll = (wheel.y * 3.0).round() as usize;  // wheel.y<0 时 = 0！
```

Rust 中负浮点 `as usize` 饱和为 0（不是回绕也不是 panic）。凡可能为负的量
先落 `isize`/`i64` 再按符号分流。clippy 的 `cast_possible_truncation`
类 lint 可静态拦截此类问题，值得在本项目启用。

## 核心教训 4：布局几何实测优于常量估算

任何"容器高度 ÷ 已知行高"式估算，都在假设字体度量、UI 缩放、行距设置三者
恒等于编码时的常量。Bevy 提供 `ComputedNode` 就是让你读布局引擎的**结算结果**。
凡是"数量随显示环境变化"的推导，数据源必须是运行时实测值，常量只配当 fallback。

## 教训 5：输入侧协议不能超过输出侧的解析能力（shell 回退决策）

为修复 Home/End 与中间插入，曾把 PTY 启动的 shell 从固定 `sh` 改为解析
`$SHELL` → bash → zsh。用户否决并回退，理由成立：

- 本终端渲染器是**逐行文本模型 + 全量剥离 ANSI**——无颜色、无光标寻址、无区域重绘
- zsh 主题 / 右侧提示符 / p10k、fish 的富转义输出依赖 VT 光标寻址才能正确成像；
  塞进朴素模型的结局是转义序列被剥掉而排版效果丢失 → 错位、残留、乱码
- 复盘发现"按键没反应"的真实病灶在**协议层缺口**：控制字符被静默丢弃（Ctrl+Z 等）、
  `Key::Escape` 未转发（vim 出不了插入模式）——与选哪个 shell 无关

提炼出的原则：

1. 模拟器的字节转发与渲染器的解析是两层独立契约，**输入侧协议选择以渲染端解析能力为准**。
   裸 POSIX shell 输出流最可预测，是朴素渲染器的正确搭档。
2. 症状出现在哪一层，就修哪一层；用换上层组件（换 shell）绕过底层缺陷，
   既治不了病，还会引入新的适配负担。
3. 升级路径记录在案：先实现真 VT 模拟（256 色 / 光标寻址 / 差分重绘），
   富 shell 适配才有讨论资格。

## 手势/命中检测 checklist（增补）

在 `window-gesture-isolation.md` 基础上追加：

- [ ] 光标坐标来源与对比目标的坐标空间一致（逻辑 vs 物理）
- [ ] 缩放 ≠100% 的屏幕上实测过（sf=1.0 会掩盖整类 bug）
- [ ] 命中检测对齐框架内置系统（如 ui_focus_system）的实现方式
- [ ] 浮点差值转整数索引前经过有符号类型
- [ ] 视口/容量类推导使用实测几何，常量仅作未布局时的 fallback
- [ ] 新假设必须能同时推演全部已知症状（含反例症状）才算候选根因
- [ ] 输入侧协议（shell/子程序）的能力不超过渲染端的 VT 解析水平
